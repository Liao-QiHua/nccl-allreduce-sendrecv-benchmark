# 执行链路与计时边界

本文描述需要在 NCCL v2.28.9-1 上核实的执行结构。函数名和分支必须以该 Tag 的实际源码及运行日志为准；此图是插桩设计蓝图，不是声称已经实测的调用图。

## 1. AllReduce 主路径

```text
Application
  |
  +-- ncclAllReduce
        |
        +-- enqueue / collective task append
              |
              +-- group end / task preparation
                    |
                    +-- algorithm + protocol selection
                    |
                    +-- collective plan / chunking
                          |
                          +-- work upload
                          |
                          +-- kernel launch
                                |
                                +--------------------> GPU Rank 0 kernel
                                |                         |
                                |                         +-- work load/dispatch
                                |                         +-- selected algorithm
                                |                         +-- selected primitive
                                |                         +-- peer wait / data / reduce / notify
                                |
                                +--------------------> GPU Rank 1 kernel
                                                          |
                                                          +-- work load/dispatch
                                                          +-- selected algorithm
                                                          +-- selected primitive
                                                          +-- peer wait / data / reduce / notify
```

## 2. SendRecv 主路径

每个 Rank 在同一个 NCCL Group 中提交一个 Send 和一个 Recv，目标 Rank 为对端。两个 Rank 同时执行，因此该测试测量的是双向 paired SendRecv，不是单向 ncclSend 的孤立延迟。

```text
Rank 0 Host                         Rank 1 Host
    |                                   |
    +-- GroupStart                      +-- GroupStart
    +-- ncclSend(to rank 1)             +-- ncclSend(to rank 0)
    +-- ncclRecv(from rank 1)           +-- ncclRecv(from rank 0)
    +-- GroupEnd                        +-- GroupEnd
    |                                   |
    +---------- CUDA work queued -------+
                    |
             +------+------+
             |             |
          GPU Rank 0    GPU Rank 1
             |             |
          P2P send/recv primitives and transport-specific synchronization
```

## 3. 串行与并行关系

- 单个 Host 线程内的 API 调用、Group 处理和 launch 函数存在程序顺序。
- 两个 MPI Rank 的 Host 线程并发执行；MPI Barrier 只用于每轮计时前对齐，不在计时区间内。
- Kernel launch 返回不表示 GPU 工作完成。
- 两张 GPU 的 Kernel 在各自 Stream 上执行，可以并行。
- 如果所选 Transport 需要 Proxy，Proxy 线程可能与 GPU Kernel 并行推进；是否存在必须由运行时连接器和事件确认。
- GPU 内部 peer wait 可能等待对端 GPU 的数据发布或同步，因此 Kernel 时间包含实际等待。
- E2E 从 API 调用前计时，到本 Rank Stream 完成；每轮以两 Rank 的最大值作为该轮样本。

## 4. 建议事件字段

Host 事件：rank、thread id、operation sequence、event id、parent event id、begin_ns、end_ns、algorithm、protocol、channel/work id。

Device 事件：rank、CTA/channel、work id、stage id、start cycle、end cycle、duration cycles。

不能未经时钟校准直接比较两个 GPU 的绝对 clock64 时间戳。应先在每张 GPU 上计算阶段 duration，再比较 duration。

## 5. 8 Byte 阶段拆分

AllReduce 可能包含本地数据访问、跨 GPU 数据交换、规约、写回和同步。SendRecv 不包含 AllReduce 求和阶段，应拆为数据读取、发送/接收、等待/同步和完成发布。不同协议及 Primitive 的实现并不相同，必须以实际模板特化和控制分支为准。

不要把某个 Primitive 的逻辑阶段表机械套用到所有 Primitive。对于未执行的阶段记录 N/A。

## 6. 时间统计注意事项

1. Host API duration 是 CPU 函数驻留时间。
2. Kernel duration 是 GPU 执行区间，不等于 Host API duration。
3. Proxy duration 是 Proxy CPU 线程的活动时间，不等于 GPU 等待时间。
4. 不将父函数和子函数耗时相加。
5. 并行区间不能简单求和推导 E2E。
6. 先测未插桩 baseline，再测插桩版本，量化插桩扰动。
