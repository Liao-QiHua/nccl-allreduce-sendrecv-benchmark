# NCCL Reduce / SendRecv Benchmark 测试设计与实施文档

## 1. 测试目标

基于 NVIDIA/nccl v2.28.9-1，在同机两张 RTX PRO 5000（PCIe 连接）上，以两个 MPI 进程、每进程一张 GPU，测试 AllReduce 与 Send/Recv 的延迟。

分为两类：
- 端到端：AllReduce 和 SendRecv 均测试 8 Byte、16 KiB、8 MiB。
- 阶段拆解：只针对 8 Byte，分析 Host 函数和 GPU Kernel/Device 阶段。

每种协议独立运行 SIMPLE、LL。每个 operation/payload 预热 20 次，正式测量 100 次，报告算术平均值。

## 2. 固定环境与参数

| 项目 | 配置 |
|---|---|
| NCCL | NVIDIA/nccl v2.28.9-1 |
| GPU | 2 × RTX PRO 5000 |
| 拓扑 | 同机 PCIe；运行前检查 P2P |
| MPI | 2 ranks；每进程一张 GPU |
| 数据类型 | FP32 |
| AllReduce | ncclSum |
| SendRecv | 每个 Rank 向对端发送，同时从对端接收 |
| Payload | 8 Byte、16 KiB、8 MiB |
| Protocol | SIMPLE、LL 分开强制 |
| Algorithm | 自动选择，记录真实选择 |
| Warmup / Measure | 20 / 100 |
| 阶段插桩 | 仅 8 Byte |

8 Byte 指两个 FP32 元素，不是 8B 个元素。16 KiB=16,384 Byte；8 MiB=8,388,608 Byte。

## 4. 协议和算法控制

分别设置：
```bash
NCCL_PROTO=Simple
NCCL_PROTO=LL
```

本测试只强制协议，不强制算法：不设置 NCCL_ALGO，让 NCCL 自动选择算法，并从 INFO 日志确认实际选择。若要研究固定 Ring，应增加独立诊断实验，不能把 Ring 专项结果当成自动选择结果。

如果某个算法/协议组合没有可用实现或运行失败，记录为该配置不可用；不能把实际采用其他协议的结果标记为 LL/SIMPLE。

## 5. 端到端测量定义

每轮测量顺序：
1. MPI_Barrier 在计时区间外对齐两个 Rank。
2. Host monotonic timer 开始。
3. 调用 ncclAllReduce，或 ncclGroupStart + ncclSend/ncclRecv + ncclGroupEnd。
4. API timer 结束。
5. cudaStreamSynchronize 等待 Stream 完成。
6. E2E timer 结束。
7. MPI_Allreduce(MAX) 在本轮计时区间外取两个 Rank 的最大耗时。

对 100 个 per-iteration rank-max 样本求算术平均值。

- Host API time：CPU 在 API 调用中的驻留时间。
- E2E time：从 API 提交前至 Stream 完成的墙钟时间。
- 两者不能相加；GPU 执行和 Host 后续工作可能重叠。
- 这是逐次同步的单操作延迟测试，不是批量异步吞吐测试。

## 6. 数据正确性

AllReduce：Rank 0 输入全部为 1.0，Rank 1 输入全部为 2.0；所有输出应为 3.0。

SendRecv：Rank 0 输入全部为 1.0，Rank 1 输入全部为 2.0；每个 Rank 接收对端数据，因此 Rank 0 输出应为 2.0，Rank 1 输出应为 1.0。

Benchmark 在每种 operation/payload 结束后检查全部 FP32 输出元素。

## 7. 执行流程

### 7.1 检查拓扑

```bash
nvidia-smi -L
nvidia-smi topo -m
nvidia-smi topo -p2p p
```

确认两张 GPU 可见、Rank 到 GPU 映射正确，并记录 P2P 能力。不能仅根据硬件型号假设 P2P 一定可用。

### 7.2 获取 NCCL 基线

```bash
git clone https://github.com/NVIDIA/nccl.git
cd nccl
git checkout v2.28.9-1
git rev-parse HEAD
```

保存 commit SHA。先构建未插桩 NCCL 作为 baseline。

### 7.3 编译 Benchmark

```bash
export CUDA_HOME=/usr/local/cuda
export NCCL_HOME=/path/to/nccl-install
bash scripts/build.sh
ldd ./reduce_sendrecv_bench | grep nccl
```

确认运行时链接的是目标 NCCL 版本。

### 7.4 运行完整测试

```bash
bash scripts/run_all.sh
```

脚本分别设置 Simple 和 LL。每个协议覆盖 AllReduce/SendRecv 和三个 payload。输出 CSV 与 NCCL 日志。

建议环境变量：
```bash
export NCCL_DEBUG=INFO
export NCCL_DEBUG_SUBSYS=INIT,COLL,TUNING,P2P
```

### 7.5 阶段插桩

仅对 8 Byte 执行插桩版运行：
- AllReduce + SIMPLE
- AllReduce + LL
- SendRecv + SIMPLE
- SendRecv + LL

每项仍预热 20 次、测量 100 次。插桩版和未插桩版结果分开保存。

## 8. Host 函数计时设计

按 v2.28.9-1 实际调用链确认后插桩，候选边界：
- AllReduce / SendRecv API 入口和返回。
- collective/P2P enqueue、task append。
- Group End 与任务调度。
- 算法、协议选择。
- Plan、Work upload、Kernel launch。
- Proxy op 创建、提交和 Progress（仅实际路径存在时）。

记录 rank、thread id、operation sequence、event id、begin/end monotonic timestamp、算法、协议、channel/work id（可得时）。

使用固定容量 thread-local buffer；热路径不打印、不动态分配、不加锁。父子区间不可相加；父区间用于时间线，互斥叶子区间用于耗时归因。

## 9. GPU Kernel / Device 阶段计时

先确认运行时实际选择的算法、协议和模板特化。分别处理 Collective 与 P2P Send/Recv Device 路径。

建议阶段：
1. Kernel 入口与 Work batch 装载。
2. Work dispatch。
3. 算法或 P2P 操作阶段。
4. peer/flag wait。
5. 数据读取与 PCIe P2P 访问。
6. Reduce（仅 AllReduce 适用）。
7. 数据写回、fence、notify。
8. Kernel 完成。

不同 Primitive 的控制流不同，不能假设所有操作都经过相同阶段。使用 clock64() 计算单 GPU 本地 duration，不比较两张 GPU 的绝对 clock64 时间戳。避免全局 atomic、printf 和动态分配。

## 10. Proxy 与串并行分析

PCIe P2P 直连时可能没有 Proxy Progress，但不能仅凭 PCIe 拓扑推断 Proxy 必为空。检查实际 Connector 的 proxyProgress、Transport 和 CUDA memcpy/CE 配置。

无 Proxy 工作时标记 N/A，而不是 0。Host、Proxy、GPU 事件可能重叠；E2E 由依赖关键路径决定，不是各阶段时间简单求和。

时间线至少分轨展示 Rank 0/Rank 1 的 Host 主线程、Proxy（如有）、GPU。Device 时间戳只在本 GPU 内计算 duration；跨 Rank 对比持续时间，不直接比较未经校准的绝对设备时钟。

## 11. Patch 质量要求

当前 instrumentation 目录是插桩设计，不是已验证 Patch。完成标准：
1. 记录上游 Tag 和 commit SHA。
2. 未插桩基线可编译。
3. 插桩版本可编译。
4. AllReduce/SendRecv × SIMPLE/LL 四种 8 Byte 组合正确性通过。
5. 日志确认实际算法、协议、Transport。
6. 对比插桩前后 E2E，报告插桩开销。
7. 保存 CUDA、Driver、编译器、GPU 拓扑和运行日志。
8. 生成可复现的正式 Patch。

未经构建和远端 GPU 验证的代码，不得标记为已验证 Patch。
